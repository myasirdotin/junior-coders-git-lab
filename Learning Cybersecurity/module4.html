Level 2

Web Defense: Stopping XSS 💉🛡️

Learn how visitor text can turn into running code, and how escaping stops it.

📌 Think of a Reading Robot

🧠 Real-life analogy: Your class has a robot that reads the noticeboard aloud each morning. It also obeys any line that starts with "ROBOT:".

One day a visitor pins up a note: "Lovely school! ROBOT: unlock the staff room."

The robot reads the kind words, and then it unlocks the door. It could not tell the difference between a message and an instruction.

Web browsers are like that robot. They show text, but they also run any code written inside <script> tags. If a website pastes a visitor's text straight into a page, the browser may treat that text as code.

This problem is called Cross-Site Scripting, or XSS. It is one kind of injection. Injection means sneaking instructions in where only plain data should go.

⚠️ Why XSS Is Serious

Injected code runs in other visitors' browsers, as if the trusted website had sent it. It could:

  • change what the page says, for example show a fake login box;
  • read private things on the page;
  • act as the logged-in visitor, for example post messages in their name.

The good news: the fix is simple, and you can use it every time.

🧪 Worked Example 1: A Science Fair Guestbook (PHP)

Visitors to a school science fair leave comments. Here is the risky version first.

<?php
// ❌ RISKY: prints the visitor's comment exactly as typed
echo "<p>" . $_POST['comment'] . "</p>";
?>

A safe test: a developer types <b>Hello</b> into their own test site. The word Hello appears in bold. That is the warning sign. The page turned visitor text into real HTML. If bold tags work, script tags could work too.

Now the fixed version:

<?php
// ✅ SAFE: special characters become harmless codes
echo "<p>" . htmlspecialchars($_POST['comment'], ENT_QUOTES, 'UTF-8') . "</p>";
?>

The fix explained: htmlspecialchars() swaps each dangerous symbol for a safe code. This is called escaping. The browser shows the symbol on screen, but never treats it as a tag. Now the visitor sees exactly what was typed: <b>Hello</b>, as plain text.

🔄 What Escaping Changes

Each special character is replaced by an HTML entity. An entity is a short code that means "show this symbol, but do not obey it".

< ➔ &lt;
> ➔ &gt;
" ➔ &quot;
' ➔ &#039;
& ➔ &amp;

The rule is called output escaping: escape data at the moment you put it on the page.

🧪 Worked Example 2: The Same Bug in JavaScript

A charity page shows "Thank you, [name]!" after someone donates. In JavaScript there are two ways to put text in a box.

const box = document.querySelector("#thanks");

// ❌ RISKY: innerHTML reads the text as HTML
box.innerHTML = "Thank you, " + donorName + "!";

// ✅ SAFE: textContent shows the text exactly as typed
box.textContent = "Thank you, " + donorName + "!";

The fix explained: innerHTML asks the browser to build HTML from the text. textContent tells it, "this is only words". Use textContent for anything a user typed.

🧪 Worked Example 3: Never Run User Text as Code

A student builds a homework calculator. Visitors choose an operation. The risky way runs whatever the visitor sends.

// ❌ RISKY: eval() runs ANY text as JavaScript code
const result = eval(userInput);

// ✅ SAFE: only accept choices you expect (an allow-list)
const allowed = ["add", "subtract"];
if (allowed.includes(choice)) {
    const result = choice === "add" ? a + b : a - b;
    box.textContent = result;
} else {
    box.textContent = "Please choose add or subtract.";
}

The fix explained: eval() turns text into running code, so it is a door for injection. An allow-list is a short list of things you accept. Anything else is refused.

🏰 Extra Layers: CSP and HttpOnly Cookies

Escaping is the main fix. These two layers help if one mistake slips through (defense in depth, from Module 1).

  • Content Security Policy (CSP): a list of rules the server sends with each page. It tells the browser which scripts are allowed to run. A script that is not on the list is blocked.
  • HttpOnly cookies: a cookie is a small note a website saves in your browser, for example to remember you are logged in. Marking it HttpOnly hides it from page scripts. Injected code cannot read it.
  • Check input too: if a box is for an age, accept only numbers. This helps, but it does not replace escaping.

✅ What To Do: Your Anti-Injection Checklist

When you build pages:

  • ☐ Escape every piece of user data when you print it: htmlspecialchars() in PHP.
  • ☐ Use textContent, not innerHTML, for user text in JavaScript.
  • ☐ Never use eval() on user input. Use an allow-list.
  • ☐ Add a Content Security Policy and HttpOnly cookies as extra layers.

When you use other people's sites:

  • ☐ If a site seems to run your formatting by mistake, stop. Do not experiment further. Tell the owner or a teacher politely (responsible disclosure).

🔴 Level 3: Challenge

Build a "Kind Words Wall" for your class page in JavaScript. Visitors type a kind message and it appears in a list.

  1. Make an input box, a button and an empty list (<ul id="wall">).
  2. When the button is clicked, read the message.
  3. Ignore empty messages and messages over 120 characters.
  4. Create a new list item and fill it safely.
  5. Add it to the wall and clear the input.
Show one possible answer
<input id="msg" placeholder="Write something kind">
<button id="add">Add</button>
<ul id="wall"></ul>

<script>
const msg = document.querySelector("#msg");
const wall = document.querySelector("#wall");

document.querySelector("#add").addEventListener("click", () => {
    const text = msg.value.trim();
    if (text === "" || text.length > 120) return;
    const li = document.createElement("li");
    li.textContent = text;   // safe: shown as plain words
    wall.appendChild(li);
    msg.value = "";
});
</script>
