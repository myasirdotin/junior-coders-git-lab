Level 2

Database Defense: Defeating SQLi 💉🗄️

Learn how mixing visitor text into database commands goes wrong, and how prepared statements fix it.

📚 Think of a Library Request Slip

🧠 Real-life analogy: In a big library, you write a book title on a slip. A helper robot reads the whole slip and does what it says.

A careless slip reads: "Fetch the book: Rivers of Asia. Also give me the staff-room key." The robot fetches the book and hands over the key!

A safer library uses a printed form. It has one locked box marked "Title only". Whatever is written in that box is treated as a title, nothing more.

Websites talk to their database (an organised store of data) using a language called SQL. SQL injection (SQLi) happens when a visitor's typing gets mixed into an SQL command. Then the database may obey the visitor's words as commands.

🗄️ A Tiny Bit of SQL

An SQL command is a sentence for the database. This one asks for the titles of books by one author:

SELECT title FROM books WHERE author = 'Ibn Sina';
  • SELECT title: give me the title column.
  • FROM books: look in the books table.
  • WHERE author = 'Ibn Sina': only rows with this author.
  • The quote marks ' ' show where the data starts and ends.

Those quote marks are the weak spot. If a visitor's text contains a quote, it can end the data early. Then the rest of the text is read as SQL commands.

🧪 Worked Example 1: A Search Box That Breaks

A school library search page builds its SQL by gluing text together. Gluing strings together is called concatenation.

<?php
// ❌ RISKY: the visitor's text is glued into the SQL command
$sql = "SELECT title FROM books WHERE author = '" . $author . "'";
?>

An innocent test: a student searches for the author O'Hara. The command becomes:

SELECT title FROM books WHERE author = 'O'Hara'
                                         ↑ the data ends here early
                                           "Hara'" is now read as SQL → error

The page crashes with an error. That error is the warning sign. If one quote can change the command, carefully chosen words could change it more.

What attackers do with this: on a login form, they might type text such as ' OR '1'='1. Because '1'='1' is always true, a badly built query could let them in without the right password. We study this only so we can block it.

🛡️ Worked Example 2: The Fix, Prepared Statements

A prepared statement is the "printed form" from our analogy. You send the SQL command first, with a ? where data will go. The ? is called a placeholder. Then you send the data separately.

<?php
// ✅ SAFE: command and data travel separately
$stmt = $pdo->prepare("SELECT title FROM books WHERE author = ?");
$stmt->execute([$author]);
$books = $stmt->fetchAll();
?>

The fix explained:

  • $pdo is PHP's connection to the database. PDO is the PHP tool for talking to databases.
  • prepare() sends the command with its empty ? box. The database fixes the shape of the command now.
  • execute([$author]) fills the box. Whatever the visitor typed is treated as data only, even quotes.
  • Now O'Hara simply searches for the author O'Hara. No error, no injection.

🔐 Worked Example 3: A Safe Login (Modules 2 + 5)

Login pages need both lessons: prepared statements and password hashes.

<?php
// 1. Find the user with a placeholder (no gluing!)
$stmt = $pdo->prepare("SELECT id, password_hash FROM users WHERE username = ?");
$stmt->execute([$_POST['username']]);
$row = $stmt->fetch();

// 2. Check the password against the saved hash (Module 2)
if ($row && password_verify($_POST['password'], $row['password_hash'])) {
    echo "Welcome back!";
} else {
    // Same message for both mistakes, so we don't reveal which was wrong
    echo "Username or password is incorrect.";
}
?>

Why this is good: the password is never put into SQL at all. The database only finds the user. PHP checks the password with password_verify().

📏 Three More Database Safety Rules (Iḥsān)

  1. Least privilege: the website's database account gets only the powers it needs. A search page only needs to read. It should not be able to delete tables.
  2. Hide error details: show visitors a friendly message like "Something went wrong". Save the full error in a private log for developers. Detailed errors give attackers clues.
  3. Placeholders are for values only: a ? cannot hold a column name. If visitors choose a sort order, use an allow-list such as ["title", "author"].
💡 Placeholders are not just for logins. Use them in every query that includes user data: searches, sign-ups, updates and deletes.

✅ What To Do: Your Database Checklist

  • ☐ Never glue user input into SQL. Use prepare() and ? placeholders every time.
  • ☐ Store passwords with password_hash(); check them with password_verify().
  • ☐ Give the website's database account only the powers it needs.
  • ☐ Show friendly errors to visitors and keep details in a private log.
  • ☐ Use allow-lists for column names and sort orders.
  • ☐ Only test your own projects. Never try injection on a real website.

Fill in the blanks: SQL injection happens when user input is ________ into an SQL command. In a prepared statement, the ? is called a ________.

Show answer
Glued (concatenated). Placeholder. It holds data that is never treated as a command.

🟡 Level 2: Apply

A charity website shows a donor their past gifts. Rewrite this risky code as a prepared statement.

$sql = "SELECT amount, gift_date FROM donations WHERE donor_email = '" . $email . "'";
$rows = $pdo->query($sql)->fetchAll();
Show answer
$stmt = $pdo->prepare("SELECT amount, gift_date FROM donations WHERE donor_email = ?");
$stmt->execute([$email]);
$rows = $stmt->fetchAll();

The email now travels separately from the command, so quotes in it cannot change the SQL.

🔴 Level 3: Challenge

Plan a safe "My Library Loans" page. A logged-in student sees the books they have borrowed, sorted by title or by due date.

  1. Write the query with a placeholder for the student's ID.
  2. Take the student's ID from the login session, not from the web address.
  3. Let the student choose the sort, using an allow-list.
  4. Show a friendly message if something goes wrong.
Show one possible answer
<?php
$sortChoices = ["title", "due_date"];
$sort = in_array($_GET['sort'] ?? '', $sortChoices) ? $_GET['sort'] : "due_date";

try {
    $stmt = $pdo->prepare("SELECT title, due_date FROM loans WHERE student_id = ? ORDER BY $sort");
    $stmt->execute([$_SESSION['student_id']]);
    $loans = $stmt->fetchAll();
} catch (PDOException $e) {
    error_log($e->getMessage());   // private log for developers
    echo "Sorry, we could not load your loans. Please try later.";
}
?>

$sort is safe to place in the SQL because it can only be one of two words we chose.
