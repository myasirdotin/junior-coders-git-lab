OWASP #1 vulnerability. Learn how to enforce ownership boundaries, prevent IDOR, and defeat request forgery.

Broken Access Control & IDOR Flaws

An **Insecure Direct Object Reference (IDOR)** occurs when an application provides direct access to records based on user-supplied input (like an ID in the URL) without checking whether the logged-in user owns that record:

// ❌ VULNERABLE: Anyone can change ?id=50 to ?id=51 and view other students' records!
$report = $db->query("SELECT * FROM grades WHERE id = " . $_GET['id']);

// ✅ SECURE ACCESS CONTROL: Enforce ownership with session verification!
$stmt = $pdo->prepare("SELECT * FROM grades WHERE id = :id AND student_id = :session_user");
$stmt->execute([':id' => $_GET['id'], ':session_user' => $_SESSION['user_id']]);

Cross-Site Request Forgery (CSRF)

CSRF tricks an authenticated victim into executing unwanted actions on a trusted web application where they are currently logged in:

1. Anti-CSRF Synchronizer Tokens

Insert a secret, random token into every form. External sites cannot read this token due to the Same-Origin Policy.

<input type="hidden" name="csrf" value="token_xyz">

2. SameSite Cookie Attributes

Tell the browser not to attach session cookies to requests originating from external third-party domains.

Set-Cookie: session=123; SameSite=Strict; Secure

🧪 Your Turn: Audit URL Parameters

Review this route: GET /account/delete?user_id=15. Why is this flawed in two separate ways?

  • 1. State change on GET: Dangerous actions like deleting must always use POST or DELETE with CSRF tokens.
  • 2. IDOR parameter: The server should delete the account belonging to $_SESSION['user_id'] rather than trusting a user-supplied ID in the URL!
