Level 3

Broken Access Control & CSRF 🚪🎭

Make sure people can only see and change what is theirs, and stop forged form requests.

🗄️ Think of the School Lockers

🧠 Real-life analogy: Every student has a numbered locker. The caretaker has a master key.

One day a student says, "Please open locker 51." The caretaker opens it without asking, "Is locker 51 yours?" Now anyone can open anyone's locker just by saying a number.

The lock is fine. The checking is missing.

Two words help here:

  • Authentication: proving who you are (logging in).
  • Authorization: checking what you are allowed to do.

Access control is the set of authorization rules. When those rules are missing or wrong, we call it broken access control. The OWASP Top 10 is a respected list of the biggest website security risks, made by an open community of experts. Broken access control is number one on it.

🔢 Worked Example 1: Changing a Number in the Address (IDOR)

A school portal shows report cards at addresses like this:

https://portal.greenfield-school.org/report.php?id=50

Bilal sees his report at id=50. What if the server shows report 51 to anyone who asks? This bug has a long name: Insecure Direct Object Reference, or IDOR. In plain words: the server hands over a record just because you asked for its number, without checking it is yours.

<?php
// ❌ RISKY: shows ANY report whose number is in the address
$stmt = $pdo->prepare("SELECT * FROM reports WHERE id = ?");
$stmt->execute([$_GET['id']]);
?>

This uses a placeholder, so it is safe from SQL injection (Module 5). But it still has no ownership check.

<?php
// ✅ SAFE: only shows the report if it belongs to the logged-in student
$stmt = $pdo->prepare("SELECT * FROM reports WHERE id = ? AND student_id = ?");
$stmt->execute([$_GET['id'], $_SESSION['user_id']]);
$report = $stmt->fetch();

if (!$report) {
    http_response_code(404);
    exit("Report not found.");
}
?>

The fix explained: $_SESSION['user_id'] comes from the login, on the server. The visitor cannot change it. The query now asks for "report 50 and belonging to this student". Report 51 returns nothing.

👩‍🏫 Worked Example 2: Hiding a Button Is Not Enough

A library website hides the "Delete book" button from students. But the delete page itself still works for anyone who visits it. Hiding a button is not security. The server must check every request.

<?php
// ✅ At the top of delete_book.php: only librarians may continue
if (($_SESSION['role'] ?? '') !== 'librarian') {
    http_response_code(403);   // 403 means "Forbidden"
    exit("Sorry, only librarians can delete books.");
}
// ...delete code runs only after the check...
?>
💡 Check permissions on the server, on every page that reads or changes private data. Anything in the browser can be changed by the visitor.

✉️ Cross-Site Request Forgery (CSRF)

When you log in, the website saves a session cookie in your browser. A cookie is a small note that says "this visitor is logged in". Your browser sends it automatically with every request to that site.

CSRF uses that habit. A different website secretly makes your browser send a request to a site where you are logged in. Your cookie goes along, so the request looks like it came from you. "Forgery" means a fake made to look real.

🧠 Analogy: someone slips a filled-in permission slip into your school bag. You hand in your bag, and the office stamps the slip because it is in your bag. The office should have checked for the secret stamp that only it gives out.

🛡️ Worked Example 3: Adding a CSRF Token

The fix is a CSRF token: a long random secret placed in each form. Other websites cannot read it. The browser's same-origin policy stops one website from reading pages of another. So a forged request will not have the right token.

<?php
// Step 1: make a random token once per login session
if (empty($_SESSION['csrf'])) {
    $_SESSION['csrf'] = bin2hex(random_bytes(32));
}
?>
<!-- Step 2: put it in the form as a hidden field -->
<form method="post" action="update_email.php">
    <input type="hidden" name="csrf" value="<?= $_SESSION['csrf'] ?>">
    <input type="email" name="email">
    <button>Save</button>
</form>

<?php
// Step 3 (in update_email.php): refuse the request if the token is wrong
if (!hash_equals($_SESSION['csrf'], $_POST['csrf'] ?? '')) {
    http_response_code(403);
    exit("This form has expired. Please reload the page.");
}
?>
  • random_bytes(32) makes 32 random bytes. bin2hex() turns them into readable letters and digits.
  • hash_equals() compares the two tokens safely.
  • Use method="post" for anything that changes data. Never change or delete data from a plain link.

Extra layer: cookies can carry a SameSite setting. SameSite=Lax or SameSite=Strict tells the browser not to send the cookie with most requests that start on other websites.

Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax

✅ What To Do: Your Access Control Checklist

  • ☐ On every private page, check on the server: is this user allowed to see or change this record?
  • ☐ Take the user's ID from the session, never from the address or a form field.
  • ☐ Give each role only the powers it needs (least privilege, Module 1).
  • ☐ Use POST forms with a CSRF token for every change.
  • ☐ Set cookies with HttpOnly, Secure and SameSite.
  • ☐ As a user: log out of shared computers, and report it if you ever see someone else's data.

🏆 Practice: three levels

🟢 Level 1: Recall

What is the difference between authentication and authorization? What does CSRF stand for?

Show answer
Authentication proves who you are. Authorization decides what you are allowed to do. CSRF stands for Cross-Site Request Forgery.

🟡 Level 2: Apply

Review this link from a school website. It is flawed in two different ways. Name both and say how to fix them.

<a href="account_delete.php?user_id=15">Delete my account</a>
Show answer
  1. Change from a plain link (GET): another website could trigger it (CSRF). Fix: use a POST form with a CSRF token.
  2. IDOR: the user ID comes from the address, so anyone could change 15 to another number. Fix: delete the account of $_SESSION['user_id'] instead.

🔴 Level 3: Challenge

A community food bank lets volunteers edit their own shift times. Design the secure "Edit my shift" feature.

  1. Decide how the server knows who the volunteer is.
  2. Write the query that updates a shift only if it belongs to them.
  3. Protect the form against CSRF.
  4. Say what organisers can do that volunteers cannot.
Show one possible answer
  1. From $_SESSION['volunteer_id'], set at login.
  2. $stmt = $pdo->prepare("UPDATE shifts SET start_time = ? WHERE id = ? AND volunteer_id = ?");
$stmt->execute([$_POST['start_time'], $_POST['shift_id'], $_SESSION['volunteer_id']]);
  3. The form uses method="post" with a hidden CSRF token, checked with hash_equals() before the update.
  4. Organisers (role organiser) may edit any shift and see all phone numbers. The server checks the role on those pages.
