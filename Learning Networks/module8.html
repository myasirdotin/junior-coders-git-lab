Two-way live connections, tidy API design and the tools developers use to find network problems.

REST: Tidy Rules for Web APIs 🗂️

🧠 Real-life analogy: A well-run library has a clear system. Every shelf has a label ("Science", "History"). You fill in the same kinds of slips to borrow, return or reserve a book. REST gives web services the same kind of tidy system.

An API (application programming interface) is a way for one program to ask another program for data. A web API uses HTTP (Module 6). REST is a popular style for designing web APIs. Its main ideas:

  • Each kind of thing (a resource) has a clear address, such as /books or /books/42.
  • The HTTP method says what to do with it.
  • Every request carries everything the server needs. The server does not have to remember earlier requests. This is called being stateless.

Most apps do four basic things with stored records. Together they are called CRUD: Create, Read, Update and Delete. REST maps them onto methods:

CRUDMethodExample
CreatePOSTPOST /books
ReadGETGET /books/42
UpdatePUT / PATCHPATCH /books/42
DeleteDELETEDELETE /books/42

Some methods are idempotent. That means doing them twice has the same effect as doing them once, like pressing a lift button twice. GET, PUT and DELETE are idempotent. POST is not: sending the same POST twice may create two records. So apps should guard against double-clicks on "Submit".

REST vs. WebSockets: When to Use Which

With normal HTTP, the client always speaks first. The server can only answer. The connection may stay open to be reused, but the server cannot start a message on its own. That is fine for most pages. It is a problem for live updates, such as a shared class whiteboard.

A WebSocket is a connection that stays open so that both sides can send messages at any time. This is called full-duplex: both sides can talk at the same moment, like a phone call. (A walkie-talkie, where only one person can speak at a time, is called half-duplex.)

REST (Request / Response)

The client asks, the server answers, once per request. Ideal for CRUD, form submissions and reading records.

WebSockets (Two-Way, Always Open)

One long-lived connection. Either side can send small messages whenever it likes. Ideal for live chat in a remote classroom, shared whiteboards and live attendance boards.

Worked example 1: opening a WebSocket

A WebSocket starts life as a normal HTTP request that asks to "upgrade". This example is the one used in the official WebSocket standard (RFC 6455):

GET /chat HTTP/1.1
Host: class.example.org
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

The server agrees:

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

101 Switching Protocols means: "Agreed. From now on, we stop using normal HTTP on this connection and speak the WebSocket language instead." The Accept value is worked out from the client's key. It proves the server really understood the request. Secure WebSocket addresses start with wss://, just as secure web pages start with https://.

Worked example 2: how small is a WebSocket message?

After the upgrade, each message travels in a frame with a tiny header. The header is 2 to 14 bytes:

  • 2 bytes for a short message (up to 125 bytes) from the server.
  • 2 or 8 extra bytes to write the length of a bigger message.
  • 4 extra bytes on every message from the browser to the server (a "mask" that the standard requires).
Message "Amina: present" = 14 bytes

Server → browser: 2 header + 14 = 16 bytes
Browser → server: 2 + 4 mask + 14 = 20 bytes

Same update as a new HTTP request:
often several hundred bytes of headers

That is why WebSockets suit many small, frequent updates.

The Developer's Network Diagnostic Toolkit 🧰

You have met these tools one by one. Here they are together, each matched to the layer it tests:

# 1. Can I reach it, and how long does it take? (Layer 3)
ping 1.1.1.1

# 2. Which routers does the path go through? (Layer 3)
tracert example.org (Windows) or traceroute example.org (macOS/Linux)

# 3. Does the name turn into an address? (DNS)
nslookup example.org

# 4. What does the web server answer? (Layer 7)
curl -I https://example.org/

# 5. Which connections and ports are open on my computer? (Layer 4)
netstat -an (Windows/macOS) or ss -tuan (Linux)

Worked example 3: reading tracert

tracert uses the TTL hop counter from Module 1. It first sends packets with TTL 1. The first router lowers it to 0, drops the packet and sends back a "time exceeded" note, which reveals that router. Then TTL 2 reveals the second router, and so on.

Example output (example addresses; yours will differ):

Tracing route to library.example.org [203.0.113.25]
over a maximum of 30 hops:

  1    2 ms    1 ms    1 ms  192.168.1.1
  2    9 ms    8 ms    9 ms  10.64.0.1
  3   12 ms   11 ms   12 ms  198.51.100.9
  4     *       *       *    Request timed out.
  5   24 ms   23 ms   25 ms  203.0.113.25

Trace complete.
  • Hop 1 is your own router (the default gateway from Module 3).
  • Each hop is tested three times, so there are three times per line.
  • Hop 4 shows stars. That router chose not to reply. The trace still reached hop 5, so the path works.

Worked example 4: "The site will not load" — checking step by step

ping 192.168.1.1        → replies   ✔ LAN and router OK
ping 1.1.1.1            → replies   ✔ Internet path OK
nslookup library.example.org
  → "Non-existent domain"           ✘ DNS problem!

Fix: check the spelling of the name,
or the domain's DNS records.

Work from the bottom up, as in Module 2. Stop at the first step that fails. That is where the problem is.

The DevTools Network Waterfall

In Chrome or Edge, press F12 and open the Network tab. Reload the page and click one request. The Timing view shows where the time went. Each bar matches something you learned:

  • Queueing & Stalled: the browser waiting before it can start, for example for a free connection.
  • DNS Lookup: turning the name into an IP address (Module 5).
  • Initial connection & SSL: the TCP handshake (Module 4) and the TLS handshake (Module 7).
  • Waiting for server response (TTFB, time to first byte): the request travelling there, the server working, and the first byte of the answer coming back.
  • Content Download: receiving the rest of the response. Bigger files and slower links make this bar longer.

Common Misunderstanding ⚠️

"Stars and 'Request timed out' in tracert mean the network is broken."

Not always. Many routers are set not to answer trace packets, but they still pass normal traffic. If the final hop answers, the path works.

"WebSockets are always better, because they are faster."

A WebSocket keeps a connection open the whole time, which uses server memory. For loading a page or saving a form, plain HTTP requests are simpler and work well with caches. Use WebSockets only when you need live, two-way updates.

🔐 Amānah: Use these tools only on networks and sites you own or have permission to test. Diagnostics are for fixing and caring for networks, never for spying on others.

🏆 Practice: three levels

🟢 Level 1: Recall

What does CRUD stand for? Give the usual HTTP method for each letter. Which status code means a WebSocket upgrade was accepted?

Show answer
Create (POST), Read (GET), Update (PUT or PATCH), Delete (DELETE). The upgrade answer is 101 Switching Protocols.

🟡 Level 2: Apply

A remote-classroom app sends the 20-byte message "Question 3: answer B" over a WebSocket. How many bytes travel (header + message) from the browser to the server? How many when the server sends the same message to each student?

Show answer
Browser → server: 2 + 4 (mask) + 20 = 26 bytes
Server → browser: 2 + 20             = 22 bytes

The message is under 126 bytes, so no extra length bytes are needed.

  2. Where is the problem?
  3. Write a short, polite message to the person who runs the catalogue server.

  2. The problem is in the catalogue program itself (Layer 7). 503 means the server is busy or under repair.
