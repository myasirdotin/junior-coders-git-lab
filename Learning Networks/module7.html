Level 3

HTTPS, TLS 1.3 & Digital Trust (Amānah) 🔐

Guarding the wire. Learn how modern cryptography, certificates, and CORS defend human privacy.

Why Plain HTTP Is Not Enough 📮

🧠 Real-life analogy: Plain HTTP is like a postcard. Every sorting office it passes through could read it, or even change the words. HTTPS is like a sealed, tamper-proof envelope, delivered only after the receiver shows a valid ID card.

HTTPS is HTTP sent inside a protective layer called TLS (Transport Layer Security). The newest version, TLS 1.3, is used by most websites today. TLS gives three promises:

  • Privacy: nobody on the path can read the data. This is done with encryption, which scrambles data so only someone with the right key can unscramble it.
  • Integrity: if anyone changes the data on the way, the receiver will notice.
  • Authentication: you are really talking to the website you asked for, not a fake one.

Two Kinds of Keys Working Together 🔑

A key is a long secret number used to scramble and unscramble data. HTTPS mixes two kinds of key methods:

1. Asymmetric (Public-Key) Cryptography

Uses a pair of keys: a public key anyone may see and a private key kept secret. In TLS 1.3 it is used at the start, for two jobs: to agree on a shared secret over an open network, and to let the server prove its identity with a digital signature.

2. Symmetric Cryptography (e.g. AES)

Uses one shared session key to both scramble and unscramble. It is very fast, so it protects all the data for the rest of the visit. Common choices are AES and ChaCha20.

How can two strangers agree on a secret in public?

Think of mixing paint. Both sides start with the same public colour, yellow. Each adds a secret colour of its own and sends the mix across. Then each adds its own secret colour to the mix it received. Both end up with the same final colour. Someone watching only saw the two mixes, and paint cannot be un-mixed. TLS does this with maths instead of paint. It is called a key exchange.

Browser                      Server
yellow + RED  ──── mix ────►
              ◄──── mix ────  yellow + BLUE
mix + RED                     mix + BLUE
   = yellow+red+blue  ==  yellow+blue+red
        (same secret, never sent)

Certificates: A Website's ID Card 🪪

How do you know the server is the real library.example.org? It shows a certificate. A certificate is a digital ID card. It holds:

  • the domain name it belongs to,
  • the site's public key,
  • the dates it is valid from and to,
  • the name of the Certificate Authority (CA) that signed it. A CA is a trusted organisation that checks a site really controls its domain.

Your browser and computer come with a built-in list of trusted CAs. If a certificate is not signed by one of them, has expired or is for a different name, the browser shows a warning. Free CAs such as Let's Encrypt mean every website, even a small charity's, can use HTTPS. Certificates now last only a few months, so servers renew them automatically.

Worked example 1: reading a certificate with curl

The -v flag ("verbose", meaning "tell me everything") makes curl show the TLS details.

curl -v https://example.org/ -o NUL

-o NUL throws the page away on Windows, so only the details show. On macOS and Linux, use -o /dev/null.

Example output (a few lines from curl on Linux or macOS; the names and dates here are made up, and Windows shows less):

* SSL connection using TLSv1.3 /
*   TLS_AES_128_GCM_SHA256
* Server certificate:
*  subject: CN=library.example.org
*  start date: Sep  1 00:00:00 2026 GMT
*  expire date: Nov 30 23:59:59 2026 GMT
*  issuer: O=Example Trust CA
*  SSL certificate verify ok.
  • TLSv1.3 is the TLS version. AES_128_GCM is the symmetric method chosen.
  • subject: CN=... is the name on the ID card. It must match the site you asked for.
  • verify ok means the signature chain leads back to a trusted CA.

The 1-RTT TLS 1.3 Handshake 🤝

An RTT (round-trip time) is one trip there and back, like a ping (Module 1). TLS 1.3 needs only one round trip to set up the secure channel. It happens right after the TCP handshake (Module 4).

Client ➔ Server: ClientHello (supported methods + key share)
Server ➔ Client: ServerHello (key share) + Certificate + signature + Finished, already encrypted
Client ➔ Server: Finished + the first encrypted HTTP request

The "key share" is each side's paint mix. After the first two messages, both sides compute the same session key on their own. The key itself is never sent.

Worked example 2: counting the waiting time

A student's laptop is 40 ms (one RTT) from the school portal. How long before the first encrypted request can leave?

TCP handshake      1 RTT = 40 ms
TLS 1.3 handshake  1 RTT = 40 ms
                   ─────────────
Request can go after       80 ms

With older TLS 1.2 (2 RTTs):
40 + 80 = 120 ms

TLS 1.3 saves one whole round trip on every new connection. HTTP/3 (Module 6) goes further: QUIC joins the transport and TLS handshakes, so the request can leave after about one round trip.

Headers That Protect Visitors 🛡️

A cookie is a small note a website asks the browser to keep and send back on later visits. Login cookies prove who you are, so they must be guarded. The server sets them with flags:

Set-Cookie: session=abc123; Secure;
            HttpOnly; SameSite=Lax
  • Secure: only send this cookie over HTTPS.
  • HttpOnly: page scripts cannot read it, so a harmful script cannot steal it.
  • SameSite=Lax: do not send it when other websites quietly make requests to this site.

Another header tells browsers to always use HTTPS for a site:

Strict-Transport-Security: max-age=31536000

31,536,000 seconds is 365 days. For a year, the browser will refuse plain HTTP for this site.

Same-Origin Policy & CORS

An origin is the scheme, the host name and the port together. https://app.relief.example.org and https://api.relief.example.org are different origins, because the host names differ.

The same-origin policy is a browser rule. A page's scripts may freely read answers from their own origin. For any other origin, the browser hides the answer from the script unless that server gives permission. This stops a harmful page from reading your private data from another site where you are logged in.

CORS (Cross-Origin Resource Sharing) is how a server gives that permission, with headers.

Worked example 3: a charity app calling its own API

The app at https://app.relief.example.org wants to send JSON to the API. For a request like this, the browser first sends a short "may I?" check, called a preflight, using the OPTIONS method:

OPTIONS /supplies HTTP/1.1
Host: api.relief.example.org
Origin: https://app.relief.example.org
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type

The API answers with permission:

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.relief.example.org
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: Content-Type

Now the browser sends the real POST. If the permission headers were missing, the browser would block the request and show a CORS error in the console.

Common Misunderstanding ⚠️

"The padlock means the website is safe and honest."

No. The padlock only means the connection is encrypted and the certificate matches the name in the address bar. A fake website can get a certificate for its own fake name. Always check the name carefully before typing a password.

"CORS protects my server from attackers."

CORS is a rule that browsers follow to protect their users. Tools like curl ignore it. Your server must still check logins and permissions on every request.

🔐 Amānah: When people type their names, passwords or donation details into your site, they are trusting you. HTTPS everywhere, careful cookies and tight CORS rules are how a developer keeps that trust.

🏆 Practice: three levels

🟢 Level 1: Recall

Name the three promises TLS gives. Which kind of cryptography, symmetric or asymmetric, is used for the bulk of the data, and why?

Show answer
Privacy, integrity and authentication. Symmetric cryptography carries the bulk of the data, because it is much faster.

🟡 Level 2: Apply

(1) The RTT to a server is 50 ms. How long before the first encrypted request can leave with TCP + TLS 1.3? With TCP + TLS 1.2? (2) A site sends Set-Cookie: id=77; Secure; HttpOnly. Explain each flag in one short sentence.

Show answer
TLS 1.3: 50 + 50      = 100 ms
TLS 1.2: 50 + 50 + 50 = 150 ms

Secure: the cookie is only sent over HTTPS. HttpOnly: scripts on the page cannot read it.

🔴 Level 3: Challenge

A youth group runs a charity donation site. Its app is at https://give.example.org and its API is at https://api.give.example.org. Write a short security plan:

  1. What should happen when someone visits http://give.example.org (no S)?
  2. Which header makes browsers use HTTPS for a whole year?
  3. Write the login cookie with safe flags.
  4. Write the CORS header so only the app may read API answers.
  5. How will the certificate stay valid?
Show one possible answer
  1. Reply 301 Moved Permanently to https://give.example.org.
  2. Strict-Transport-Security: max-age=31536000
  3. Set-Cookie: session=…; Secure; HttpOnly; SameSite=Lax
  4. Access-Control-Allow-Origin: https://give.example.org (one exact origin, not *).
  5. Use a free CA such as Let's Encrypt with automatic renewal, and check the expiry date each month.
